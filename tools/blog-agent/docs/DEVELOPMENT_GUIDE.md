# Development Guide

## Prerequisites

- Node.js ≥ 20.11
- Git
- GitHub CLI (`gh`) for publish testing
- The parent blog repository (with `contentlayer.config.ts` at the root)

## Getting Started

```bash
cd tools/blog-agent
npm install
cp .env.example .env
# Fill in GEMINI_API_KEY and model IDs
npm run doctor
```

## Development Workflow

### Running Commands

```bash
# Type-check without emitting
npm run typecheck

# Run tests
npm run test

# Watch mode for tests
npm run test:watch

# Full verification (typecheck + tests)
npm run verify

# View the style brief (no API calls)
npm run start -- style

# List corpus (no API calls)
npm run start -- corpus

# Dry run (full pipeline, no commits)
npm run start -- run --dry-run

# Research only (queue topics, no drafting)
npm run start -- run --research-only

# Force publish (bypass cadence gate)
npm run start -- run --force-publish --dry-run
```

### Output

- **Logs** go to `stderr` (JSON in CI, pretty-printed locally)
- **Machine-readable output** goes to `stdout` when `--json` is passed
- **Artifacts** are written to `.artifacts/` (gitignored)

## Code Conventions

### Module Structure

- Each module is a directory under `src/` with one or more `.ts` files
- No barrel exports (`index.ts`); imports name the specific file
- ESM with `.js` extensions in import paths (required for Node ESM resolution)

### TypeScript

- Strict mode with `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`
- `noEmit: true` — `tsx` executes the TypeScript directly; `tsc` is only a type checker
- Prefer `type` imports for type-only uses

### Naming

- Files: `kebab-case.ts`
- Types/Interfaces: `PascalCase`
- Functions/variables: `camelCase`
- Constants: `UPPER_SNAKE_CASE` for true constants, `camelCase` for computed values
- Zod schemas: `camelCase` for the schema object, `PascalCase` for the inferred type

### Error Handling

- Custom error classes extend `Error` with `override readonly name`
- Domain errors: `ConfigError`, `StateCorruptError`, `ModelResponseError`, `VectorMismatchError`, `TimeoutError`, `RetryExhaustedError`
- Never catch and swallow; either handle specifically or let propagate
- Log structured context with errors (`logger.error('msg', { err, ...context })`)

### Dependencies

The project has **3 runtime dependencies**:
- `@google/genai` — Gemini SDK
- `gray-matter` — YAML frontmatter parsing
- `zod` — Runtime validation

Adding new dependencies should be strongly justified. The agent deliberately avoids `dotenv`, YAML libraries, and other packages where the needed functionality is small and well-understood.

## Adding a New Gate

1. Create a `Gate` object in the appropriate file (`content.ts`, `structure.ts`, or `assets.ts`), or create a new file
2. Implement the `run(ctx: GateContext): GateFinding[]` method
3. Use `err()` for build-breaking issues and `warn()` for editorial concerns
4. Add the gate to the `cheap` array (or network/compile section) in `src/gates/run.ts`
5. Add tests

```typescript
export const myGate: Gate = {
  name: 'my-gate',
  run(ctx): GateFinding[] {
    const findings: GateFinding[] = []
    // Check something...
    if (problem) {
      findings.push(err(this.name, 'Description of the problem', lineNumber))
    }
    return findings
  },
}
```

## Adding a New CLI Command

1. Add the command name to `SUBCOMMANDS` in `src/cli.ts`
2. Write the handler function (`async function cmdXxx(): Promise<number>`)
3. Add the routing in `main()`
4. Update the `usage()` string
5. Commands that don't need the API should work without a config (see `tryLoadConfig`)

## Adding a New State File

1. Define the Zod schema in `src/state/schema.ts`
2. Add the file path to `STATE_FILES` in `src/state/store.ts`
3. Add load/save methods to the `StateStore` interface and implementation
4. Add the field to `AgentState`
5. Use `readJson()` with appropriate fallback behaviour (absent = first run; corrupt = throw)

## Git Workflow

### Branching

- `main` — Production branch
- `bot/post-<slug>-<runId>` — Agent-generated post branches
- `blog-agent-state` — Persistent state (orphan branch)

### Commits

The agent uses commit messages of the form:

```
content: <post title>

Generated by blog-agent (run <runId>).
Gates: N error(s), M warning(s).
```

### Testing Before Push

```bash
npm run verify   # typecheck + tests
```

## Debugging

### Inspect State

The state branch can be checked out locally:

```bash
git fetch origin blog-agent-state
git worktree add /tmp/agent-state blog-agent-state
cat /tmp/agent-state/state/published.json | jq .
```

### Inspect Artifacts

After a `--dry-run`, generated posts and hero images are in `.artifacts/<runId>/`:

```bash
ls -la .artifacts/
cat .artifacts/<runId>/<slug>.mdx
```

### Debug Logging

```bash
LOG_LEVEL=debug npm run start -- run --dry-run
```

### Check Available Models

```bash
npm run doctor
```

If model IDs are wrong, `doctor` prints the full list of available models.

## Local Development Flags

| Flag | Purpose |
|------|---------|
| `DRY_RUN=true` | Never commit or open a PR |
| `OFFLINE=true` | Skip network gates (external link checking) |
| `LOG_LEVEL=debug` | Verbose logging including API call details |
| `--research-only` | Queue topics without drafting |
