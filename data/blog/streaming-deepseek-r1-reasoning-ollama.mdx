When we first started running local reasoning models, the user experience was incredibly jarring. We would trigger a stream from a model like DeepSeek-R1, only to watch our screen get flooded with raw internal monologue. The model spent minutes debating its own logic, spitting out self-corrections in a chaotic wall of text. For a user waiting for a simple answer, this behavior made the application feel unpolished. We needed a clean way to separate the thinking process from the actual answer, but early streaming integrations made this incredibly difficult to parse on the fly.

## The Challenge of Raw Reasoning Streams

The core issue is that reasoning models do not output their thought process as metadata; they output it as part of the primary token stream. When streaming tokens from DeepSeek-R1, the model wraps its internal reasoning inside opening and closing think tags. If you pipe this raw stream directly to a standard markdown parser, the page renders the internal monologue as if it were the final response. The user is forced to read through hundreds of lines of self-correction before the actual answer even begins.

Standard streaming parsers operate on the assumption that the incoming text is a homogeneous stream of content. They append characters to a single buffer and flush them to the screen as quickly as possible. When we introduce structural markers like think tags, this simple model breaks down. If we try to parse the stream after it completes, we lose the benefits of real-time streaming, forcing the user to stare at a loading spinner.

If we try to parse the stream on the fly with naive regular expressions, we run into the problem of partial tokens. A chunk might arrive containing only half of a tag, or the tags might span across multiple network packets. A simple string replacement fails because it cannot account for the incomplete states of the incoming data, leading to broken layouts, leaked tags, and an unstable user interface.

## Ollama's Native Support for Think Tags

With recent updates to Ollama, we finally have a structured way to handle these reasoning tokens. The runtime now natively recognizes the think tags generated by DeepSeek-R1 and handles them systematically within the API response payload. Instead of treating the entire stream as a single, undifferentiated stream of text, the updated Ollama engine exposes the internal reasoning process as a distinct property in the JSON stream chunks.

When you make a streaming request to a model like DeepSeek-R1 using recent versions of Ollama, the engine parses the underlying model output and populates the response object accordingly. The chunks containing the model's internal reasoning are flagged, allowing developers to immediately inspect the metadata of each chunk to determine its intent. This native separation means we no longer have to guess where the reasoning ends and the final answer begins.

The payload structure for each chunk now includes a specific field indicating whether the current token belongs to the reasoning phase or the final response. By inspecting this property on the incoming JSON object, we can instantly route the token to the correct UI buffer. This native support simplifies our backend and client-side code, allowing us to build predictable, stateful parsers without relying on heavy external libraries. It shifts the burden of token categorization from our application logic to the local inference runner.

## Building a State-Based Stream Parser

To consume this stream effectively, we can implement a state-based parser using TypeScript. Instead of relying on complex regular expressions that fail on partial chunks, we build a simple state machine that tracks the current parsing context. The parser transitions between three distinct states: reading reasoning, reading content, and idle. This approach ensures that we can process every incoming chunk character-by-character, regardless of how the network splits the packets.

As the stream begins, our parser initializes in the idle state. When we receive a chunk, we inspect the native properties provided by Ollama. If the payload indicates that the token is part of the reasoning process, our state machine transitions to the reasoning state. We then append the incoming text to a dedicated reasoning buffer. This buffer is bound to a specific UI component, such as a collapsible accordion, allowing the user to watch the model's thoughts unfold in real-time.

When the model finishes its reasoning, Ollama signals the transition. Our parser detects this change, transitions our state machine to the content state, and begins appending subsequent tokens to a separate response buffer. By maintaining this explicit state, we guarantee that no reasoning tokens leak into the final output. This stateful approach is highly resilient, easy to test, and fits naturally into a modern TypeScript-based architecture, especially when leveraging clean module resolution patterns.

## Handling Edge Cases in Real-Time UI Updates

Building a real-time streaming interface requires us to handle several inevitable edge cases. Network latency can cause chunks to arrive in irregular bursts, creating a stuttering effect in the UI. If the user's connection drops momentarily, our state machine must recover gracefully without leaving the UI in an inconsistent state, such as an unclosed reasoning block that blocks the final answer from rendering.

Another common issue is handling user cancellation. If a user decides that the model is heading down the wrong path during the reasoning phase, they will likely hit the stop button. Our parser must immediately abort the underlying fetch request, tear down the stream, and clean up the active buffers. We must ensure that the UI reflects this interruption clearly, perhaps by marking the incomplete reasoning block as cancelled rather than leaving it in a permanently loading state.

We also have to consider what happens if a chunk boundary splits a key structural token. While Ollama's native tag handling minimizes this risk, network proxies or custom middleware can still slice the raw JSON payloads. Our TypeScript parser must validate the integrity of each chunk before updating the state. If a chunk is incomplete, we store the partial data in a temporary holding buffer and wait for the next chunk to arrive before attempting to parse and route the tokens.

## Architecting the Frontend for Dual-Stream Rendering

Once we have a reliable stream parser, we need to design a frontend architecture that can render these dual streams simultaneously. In a modern UI framework like React, we can manage this by maintaining two separate state variables: one for the active reasoning text and another for the final response. This allows us to decouple the rendering of the two components, ensuring that updates to the reasoning block do not trigger unnecessary refactors of the main content area.

We can design the UI with a collapsible accordion at the top of the message bubble to house the reasoning stream. While the model is thinking, the accordion remains open, displaying the raw thoughts as they are parsed. We can style this area with a distinct background color and a subtle typing indicator to signal that active processing is occurring. Once the parser transitions to the final response state, we can automatically collapse the accordion and begin streaming the final answer directly below it.

This dual-stream architecture provides a superior user experience. It respects the user's time by clearly separating the "how" from the "what." Users who want to audit the model's logic can expand the reasoning section, while those who only care about the final answer can focus entirely on the main response panel. By leveraging Ollama's native tag support and a robust state-based parser, we can transform a chaotic stream of tokens into a polished, production-ready interface.
