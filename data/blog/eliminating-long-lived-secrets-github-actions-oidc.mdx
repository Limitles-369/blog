CI/CD pipelines have historically relied on a simple but dangerous pattern: hardcoded long-lived secrets. We generate an access key in our cloud provider console, paste it into GitHub repository secrets, and pray that it never leaks. If a developer accidentally logs that environment variable or a malicious actor gains read access to the repository settings, the entire cloud infrastructure is at risk.

Rotating these keys is a classic operational burden. It requires manual coordination, risks breaking running pipelines, and often results in teams leaving keys active for months or years past their expiration. Moving to OpenID Connect (OIDC) changes the paradigm from "I have a secret" to "I can prove who I am."

## The Problem with Static Credentials

Static cloud credentials, such as AWS access keys or GCP service account JSON files, act like a master key that never expires. Because these credentials are not tied to a specific build execution, they are essentially persistent backdoors into your environment.

The security risks are significant:

- Exposure via log files or insecure storage.
- Lack of auditability regarding which specific workflow used the key.
- Increased blast radius if a single repository is compromised.
- Operational fatigue from rotating keys across dozens of workflows.
- Difficulty in enforcing granular permissions without creating hundreds of individual keys.

When we store these in GitHub Actions secrets, we are trusting the platform's storage layer entirely. If that trust is ever breached, or if an attacker gains write access to a branch that can read those secrets, our cloud environment is no longer under our control.

## Understanding OIDC in CI/CD

OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0. In the context of GitHub Actions, GitHub acts as an Identity Provider (IdP). Instead of using a static password, your workflow requests a short-lived, cryptographically signed JSON Web Token (JWT) from GitHub.

This token contains claims about the workflow: the repository, the branch, the environment, and the specific run ID. You then send this token to your cloud provider, which verifies the signature against GitHub’s public keys. If the token is valid and matches your configured trust policies, the cloud provider grants temporary, scoped access.

The token is ephemeral—it expires after the job finishes or even sooner. Even if an attacker managed to intercept the token, it would be useless within minutes. You are effectively replacing a permanent, static "password" with a dynamic, identity-based proof that is only valid for a specific, ongoing task.

## Establishing Trust Between GitHub and Cloud Providers

To enable OIDC, you must configure your cloud provider (like AWS, Azure, or GCP) to trust GitHub as an OIDC provider. This involves a few core steps:

- **Create an OIDC Provider:** In your cloud console, add GitHub (usually `token.actions.githubusercontent.com`) as a trusted identity provider.
- **Define Trust Policies:** You write a policy that tells the cloud provider what to look for in the JWT. This is where you specify the audience (`aud`), which for GitHub is typically `sts.amazonaws.com` or similar.
- **Map Claims:** The cloud provider inspects the `sub` (subject) claim in the token. This is the most critical part of the handshake.
- **Assign Roles:** You link the trusted OIDC identity to an IAM role with the specific permissions required for your deployment.

When a workflow starts, the GitHub Actions runner automatically requests the token. It passes this token to the cloud provider's CLI or SDK. The cloud provider validates the signature, confirms the audience is correct, and assumes the IAM role. This process removes the need to store any credentials in your repository settings.

## Implementing Fine-Grained Access Control

OIDC allows for much more granular control than static keys. Because the JWT contains specific claims, you can restrict access based on the repository, the branch, or even a specific GitHub environment.

You can craft trust policies that look like this:

- **Restrict by Repo:** Only allow `my-org/my-app` to assume the role.
- **Restrict by Branch:** Only allow pushes to `main` to trigger production deployments.
- **Restrict by Environment:** Require that the deployment target the `production` environment in GitHub, ensuring that manual approval gates are hit before the token is issued.

This prevents a scenario where a developer creates a rogue repository in your organization and attempts to use the same OIDC configuration to access your production cloud environment. The subject claim in the JWT would not match the expected repository string, and the cloud provider would deny the request immediately. By anchoring the identity to the repository structure, you enforce security at the infrastructure level rather than the repository configuration level.

## Refactoring Existing Workflows

Transitioning to OIDC involves removing the old secrets and updating your YAML files. First, audit your current secrets and identify which ones are used for cloud authentication.

In your workflow file:

- Remove the step that configures credentials using static keys.
- Add a `permissions` block at the job level. You must set `id-token: write` to allow the runner to request the OIDC token.
- Update your cloud-specific action (like `aws-actions/configure-aws-credentials`) to use the `role-to-assume` parameter instead of access keys.

Once you have updated the workflow and pushed the changes, you can verify the deployment. If it succeeds, you can safely delete the old `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` from your GitHub repository secrets. If a job fails, the logs will provide clear feedback on which claim—the audience, the repository, or the role—failed to validate.

## Handling Edge Cases and Troubleshooting

Transitioning to OIDC is usually smooth, but a few common pitfalls can arise.

- **Audience Mismatch:** If your cloud provider rejects the token, double-check that the `audience` in your trust policy matches exactly what the GitHub action sends.
- **Permission Scopes:** You might find that your new role has too few permissions. Because you are no longer using a single "admin" key, you may need to explicitly grant permissions for S3, CloudFront, or RDS that were previously covered by an overly permissive static key.
- **Missing Permissions:** Ensure your `permissions` block in the YAML is at the job level. If it is missing, the runner will not be able to generate the token, and the authentication step will fail silently or with an access denied error.
- **Regional Constraints:** Some cloud services require specific OIDC endpoints or may have quirks with global identity providers. Check your cloud provider's documentation if you are deploying to non-standard regions.

Don't be afraid to use the cloud provider's IAM simulation tools to debug failed requests. They often reveal exactly which claim in the JWT caused the denial.

## My Practical Take

In my experience, the effort required to set up OIDC is significantly lower than the effort required to manage and rotate secrets for a large number of projects. While the initial configuration in the cloud console feels like extra "DevOps tax," the peace of mind is worth it.

I prefer OIDC because it forces me to think about the principle of least privilege. When you have a static key, it is tempting to just give it full admin access because you don't want to deal with regenerating it if you need more permissions later. With OIDC, creating a new role for a new project is trivial. It encourages better security hygiene by default.

If you are currently using static secrets, make a plan to migrate your most sensitive pipelines first. You don't have to switch everything at once. Start with a non-production environment, get comfortable with the IAM policies, and then roll it out to your core services.

## Conclusion

Moving away from static credentials is one of the highest-impact changes you can make to your CI/CD security posture. By shifting to OIDC, you eliminate the risk of long-lived key exposure and gain a verifiable audit trail for every deployment.

Identity-based authentication is the modern standard for cloud infrastructure. While it requires an initial investment in configuring trust policies and IAM roles, the result is a more resilient, scalable, and secure deployment pipeline. As we continue to automate more of our development process, removing the reliance on static, dangerous secrets is a mandatory step for any professional engineering team. It moves the focus from managing secrets to managing identity, which is exactly where it belongs.
