The way we run TypeScript is changing. For years, our build pipelines were dominated by heavy compilation steps, transpiling every file before a single line of JavaScript could execute. Now, modern runtimes are bypassing this translation step entirely, adopting type-stripping engines that run TypeScript files directly. This simplifies our toolchains, but it also exposes a fundamental architectural tension: not all TypeScript syntax is easily stripped.

Some legacy features actually generate runtime JavaScript code, creating a compatibility gap that can break zero-build workflows. By understanding how to avoid these features, we can future-proof our applications for the next generation of JavaScript environments.

## The Shift Toward Zero-Build Runtimes

Running TypeScript directly without a build step has become increasingly practical. Modern environments like Deno and Bun pioneered this approach, and Node.js recently joined them by integrating native type stripping directly into the runtime. This changes how we manage our local development loops. Instead of spinning up heavy compiler wrappers and managing persistent caches, the runtime simply removes the type annotations and runs the remaining JavaScript immediately.

This type-stripping model is highly optimized for execution speed. By treating types as inert metadata, the runtime avoids the performance overhead of full-scale compilation and type checking. It allows us to execute scripts instantly and get immediate feedback. This approach is increasingly common for local scripts, production applications, serverless functions, and containerized deployments.

However, this model relies on a crucial assumption. The runtime assumes that removing type annotations will leave behind valid, executable JavaScript that behaves exactly as written. If your TypeScript files contain features that require the compiler to generate new runtime code, the type-stripping engine will fail or ignore them. To use this zero-build workflow, we must ensure our source files conform strictly to the rules of clean type erasure.

## Understanding Type Erasure and Its Limits

Type erasure is the process of removing type annotations, interfaces, and type imports from a source file, leaving behind pure JavaScript. In a perfect type-erased world, you can delete everything between a colon and a comma, and the remaining code is fully valid. Most modern TypeScript features adhere to this clean separation. Your interfaces, type aliases, and generic constraints exist solely to guide the compiler during type checking, vanishing completely when the code is executed.

Some early TypeScript features violate this core principle. In the early days of the language, before the ECMAScript standard caught up, TypeScript introduced features designed to fill gaps in the JavaScript specification. These features do not simply vanish during compilation; they require the compiler to emit active JavaScript code at runtime.

The most common culprits are enums, namespaces, and constructor parameter properties. Enums generate a self-referencing runtime object, namespaces generate nested objects to mimic modules, and parameter properties automatically generate class field assignments from constructor arguments. While these features provided convenience in the early 2010s, they represent a significant architectural liability today. Because they require code generation, they cannot be processed by simple type-stripping engines. If you try to run them in a native, zero-build runtime, they will either cause syntax errors or fail to execute as intended, locking your codebase into traditional, heavy build pipelines.

## Introducing the Erasable Syntax Only Flag

To bridge this gap and prevent developers from accidentally introducing non-erasable code, TypeScript introduces a compiler option: the erasable syntax only flag. When enabled in your configuration file, this flag acts as a strict, compiler-level guardrail. It instructs the TypeScript compiler to analyze your codebase and throw an error the moment it encounters any syntax that cannot be resolved through simple type stripping.

This flag provides a proactive defense mechanism for modern codebases. Instead of discovering runtime compatibility issues during deployment or when switching runtimes, the compiler flags these violations instantly in your editor and continuous integration pipelines. It guarantees that every file in your project can be safely stripped of its types and executed directly in any environment that supports native TypeScript execution.

The introduction of this flag also aligns TypeScript with the ongoing TC39 Type Annotations proposal. This proposal aims to bring type syntax directly to the browser and the ECMAScript standard by treating types as comments. Because the proposal explicitly forbids runtime-generating syntax, adopting the erasable syntax only flag ensures your codebase is structurally ready for a future where browsers might run TypeScript annotations natively without any build step at all.

## Refactoring Away from Runtime-Generating Syntax

Transitioning a codebase to comply with this flag requires systematically replacing legacy syntax with modern, standard JavaScript equivalents. The refactoring process is straightforward and yields cleaner, more predictable code.

To replace enums, the most robust alternative is using a plain JavaScript object combined with the "as const" assertion. For example, instead of declaring an enum for user roles, you can declare a standard read-only object with the roles as keys and values. To preserve type safety, you can extract the type of the object's values using the "keyof" and "typeof" operators, creating a union type that behaves exactly like an enum but compiles down to a simple, standard JavaScript object.

Namespaces are even easier to resolve. In modern development, namespaces are an obsolete pattern that has been entirely superseded by standard ECMAScript modules. Instead of nesting code within a namespace block, you should organize your code into separate files and use standard import and export statements. This not only satisfies the type-stripping compiler but also aligns your project with modern bundlers and module resolution standards.

Parameter properties in classes can be refactored by returning to standard JavaScript class syntax. Instead of prefixing constructor arguments with access modifiers like private or public to automatically generate class properties, you must explicitly declare the properties at the class level. You then assign the arguments to those properties inside the constructor body. While this requires a few extra lines of code, it ensures that your class definitions remain standard JavaScript, eliminating the need for compiler-driven code generation.

## Architectural Benefits of a Clean Compilation Path

Adopting a strictly erasable codebase provides substantial, long-term architectural benefits. By enforcing this constraint, you decouple your type-checking process from your execution environment. You can let the TypeScript compiler focus entirely on static analysis and verification, while your runtime focuses solely on fast execution. This separation of concerns simplifies your toolchain, allowing you to remove complex transpilers, custom loaders, and build wrappers from your development environment.

This clean compilation path also dramatically improves build performance. When your build tools do not need to perform complex syntax transformations or generate runtime code, they can process files at the speed of basic text manipulation. This results in faster cold starts, instantaneous hot-reloads during local development, and rapid continuous integration runs.

Ultimately, preparing your codebase for zero-build runtimes is about future-proofing. By eliminating non-standard, runtime-generating syntax, you ensure your application remains compatible with any future JavaScript runtime or standard. You protect your project from the churn of build-tooling configurations and align your codebase with the natural evolution of the web platform. The erasable syntax only flag is not just a new configuration option; it is a clear path toward a simpler, faster, and more standard development ecosystem.
